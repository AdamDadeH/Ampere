# 4. Log decision features as the policy used them

- **Status:** Accepted
- **Date:** 2026-08-15
- **Deciders:** Adam Henderson

## Context

Navigation currently runs on hand-set constants: the session/global blend midpoint, the recency
recovery window, the sustained-listen threshold. The intent is to replace them with values learned
from behaviour rather than chosen by argument. That requires training rows pairing *what the policy
saw* with *what the listener then did*.

Those inputs can either be **reconstructed** from the log afterwards, or **recorded** as the policy
computes them.

Reconstruction demonstrably works — the time-since-last-play for every repeat play was rebuilt from
`created_at` alone, and produced a usable answer. But it worked because that feature was **inert**:
nothing selected on it, so a mismatch between the reconstruction and the policy was impossible.
Once a feature drives selection, the rebuild has to reproduce exactly what the scorer computed, and
it diverges silently the moment a definition shifts — no error, just training data that describes a
policy that never ran.

And the definitions will shift. The recency curve shipped as `1 - exp(-days/7)`; measuring the log
found sustained-listen rates flat from 0 to 30 days across 145 of 179 repeat plays, which is the
range that curve is entirely about. It is wrong and will be replaced. Any feature stable enough to
reconstruct safely is a feature not worth learning.

There is a second, less obvious reason. Pooling feedback generated by different policies — Random,
Drift, Journey, hand-picked — is only legitimate if the variables those policies *selected on* are
observed. If they are, mixing policies is covariate shift, which broader coverage helps; if they are
not, the model attributes each policy's bias to whatever proxy is available.

## Decision

We will **record the feature values behind each navigation choice on the resulting play**, in a
`context_json` column on `track_feedback`.

- Each mode returns a `context` alongside its pick, written when `track_started` is recorded.
  Session logs score, affinity, freshness, global preference, blend weight, signal counts and pool
  size; Drift and Journey log their smaller sets.
- **JSON, not columns.** The feature set is expected to keep changing, and a column per feature
  would not survive that. `json_extract` keeps it queryable from SQL.
- Runtime policy parameters count as features and are logged with them: two plays made under
  different temperatures must not look identical in training data.

## Consequences

Training rows are, by construction, what the scorer saw — no reconstruction step, and no dependence
on any definition holding still. Feature definitions become free to change, which is the point.
Pooling data across navigation modes becomes sound rather than a hazard, so each mode's exploration
contributes coverage to a shared response model.

Against that:

- **Unstructured and unenforced.** Nothing validates the shape. A renamed or mistyped key produces
  training data that silently lacks a feature, and it will only surface when a fit behaves oddly.
- Storage grows with every play. Negligible at present, and unbounded in principle if the context
  keeps accreting fields.
- **Only policy-chosen plays carry it.** Manual selections and queue-order plays have `NULL`, so the
  context-aware training set is a subset of the log, and a biased one — it exists only where a
  navigation mode was running.
- Everything logged before this change lacks context permanently, and was generated by policies that
  had none of these features. That data remains fine for track-intrinsic questions and cannot train
  anything context-dependent.
- The obligation now runs the other way: a new feature that influences selection **must** be added
  to the logged context, or it reintroduces exactly the reconstruction problem this avoids.
